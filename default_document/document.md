### Post-Trade

As the final state messages on this platform for IRS and CDS orders filled on the Order Book do not include all trade details, the participant must request Spectrum Dynamics to configure an additional separate FIX session to receive post trade ExecutionReport(35=8) messages. These messages will include the client order ID generated by the participant and sent in the NewOrderSingle(35=D) or QuoteResponse(35=AJ) message.  
This is unnecessary for trades filled through Direct Order Routing since those final state messages do contain all trade details.  
ORP IRS and CDS trades can be allocated pre-trade but other asset class trades can only be allocated post-trade. To do post-trade allocation the customer must request Spectrum Dynamics to configure the additional FIX session for ExecutionReport(35=8) messages in order to receive post-trade allocation messages and send back responses.

## StandardHeader Fields

The FIX StandardHeader is included on every FIX message sent. Most of the data values of these fields should be taken care of by the FIX engine. However, there are some fields that are based on the configuration for the specific FIX session: BeginString(8), SenderCompID(49), TargetCompID(56). The usage of the SenderCompID(49) and TargetCompID(56) fields explained in the table below is from the perspective of Spectrum Dynamics. Depending on whether you are connecting into Spectrum Dynamics or Spectrum Dynamics is connecting to you, your FIX engine will need to be setup accordingly.  
Each message sent will be required to set ApplVerID(1128) and CstmApplVerID(1129) in the StandardHeader to indicate which version of the interface is being used. See also Section 3 for more information on values to use in the CstmApplVerID(1129) field.  
ApplVerID(1128) and CstmApplVerID(1129) values should not change for a given session. Spectrum Dynamics reads the values sent by the client on the first FIX message for a given session and then validates against those values for all subsequent FIX messages from the client.

## Note on FIX Field Ordering

The FIX Protocol standard specifies the following regarding ordering or sequence of fields within a FIX message:

Fields within a message can be defined in any sequence (relative position of a field within a message is inconsequential). The exceptions to this rule are:

* The general message format is composed of the standard header followed by the body followed by the standard trailer.
* The first three fields in the standard header are BeginString(8) followed by BodyLength(9) followed by MsgType(35).
* The last field in the standard trailer is the CheckSum(10)
* Fields within repeating data groups must be specified in the order that the fields are specified in the message definition within the FIX specification document. The NoXXX field where XXX is the field being counted specifies the number of repeating group instances that must immediately precede the repeating group contents.
* A tag number (field) should only appear in a message once (except within a repeating data group definition). If it appears more than once in the message it should be considered an error with the specification document.

## OrderBook Trading

This section of the document discussed the supported features of the Spectrum Dynamics OrderBook, a central limit order book trading platform. It also includes the various message flows that are supported by OrderBook. The participants may interact either via the OrderBook user interface or FIX Protocol messages as described in this document.  
**Note:** OrderBook trading is not supported for FX.

### Self-Match Prevention

In the OrderBook it is possible for orders submitted by two different traders belonging to the same entity to match. In order to allow market participants to selectively control which of their orders can self-match, the OrderBook provides the SelfMatchPreventionID(2362) field (formerly tag 7928) in the order submission messages.  
Self-match prevention will only apply at the ENFB entity level as Spectrum Dynamics will use the
SelfMatchPreventionID(2362) in combination with the entity’s ENFB ID value (PartyRole(452)=13 (Order originating firm)) as provided in the submitted message.

#### Allow self-matching for different desks

If the market participant wishes for all their orders to self-match with a resting order from the same entity but a different desk, the order submitted should omit the SelfMatchPreventionID(2362) field.  
For example, the trading firm may have a market making desk and an agency desk and do not wish to self-match orders from the same desk. The traders on each desk would submit orders without the SelfMatchPreventionID(2362) value. The desk will be provided in the order submission messages, e.g. MKT for the market making desk vs. AGENCY for the agency desk (PartySubIDType(803)=25 (Location desk), under PartyRole(452)=11 (Order originating trader)). This however would not prevent orders submitted by the agency desk from matching with resting orders from the market making desk.  
In the case where the participant is using the Spectrum Dynamics Terminal to enter orders, the Self-Match Prevention feature should be disabled on any ENFB entries used for trading.

#### Disallow self-matching

If the market participant wishes to prevent all their orders from self-matching with a resting order from the same entity, all orders submitted must include the SelfMatchPreventionID(2362) field. The value of the field must be the same on every order which should not self-match.  
In the case where the participant is using the Spectrum Dynamics Terminal to enter orders, the ENFB entities should be configured to use the same SelfMatchPreventionID(2362) value on the orders.
